# Deferred to a full version — notes for the CREW post

A running list of things deliberately left out of the proof of concept. Keeping it so
the post can say "here's what this becomes" rather than leaving people to assume the
gaps are oversights.

The framing that works: **every one of these is cut because CREW's own platform should
supply it, or because it isn't needed to prove the idea.** None of them are things that
couldn't be built.

---

## Cut because CREW should provide it

**Real member profiles.** Right now a member is a name. No title, no company, no
LinkedIn. In a real version this connects to CREW member profiles, so you'd tap a name
and see who they actually are. Building a parallel profile system for a pilot would only
create something to migrate away from.

**Sign-in.** The PoC uses one shared invite code — no accounts, no passwords, no email.
Inside CREW you'd already be signed in and it would just know who you are.

**Notifications.** The PoC sends nothing, ever. A real version might tell you when
someone joins a conference you're going to. That belongs in CREW's existing notification
channels, not a new one.

**Messaging.** Deliberately never built and never will be. Members message each other on
CREW's own platform. This app's job is to tell you *that* you should reach out, not to be
another inbox.

---

## Cut because the PoC doesn't need it to make its point

**Meetup coordination.** The obvious next step: someone proposes drinks Tuesday at
Money20/20, people vote on a time, it gets confirmed. Fully designed, not built. The PoC
is about proving the first half — knowing who's there. People can coordinate in the CREW
thread for now.

**Calendar view.** A month grid showing everyone's travel. A list already answers "who's
going where," so the grid is prettier rather than more useful.

**Session-level matching.** Knowing you're both at Money20/20 is the useful bit. Knowing
you're both in the same breakout is a much harder data problem for a much smaller payoff.

**"Considering" as a state.** Going or not going. A maybe list is noise, and it makes
every roster less trustworthy.

**Conference verification workflow.** Member-added conferences are marked unverified
until confirmed. In the PoC that's one person checking. At scale it needs a real process.

---

## Known limitations worth being upfront about

**Identity is device-bound.** Clear your browser and you re-enter the code and pick your
name again. Fine for a pilot among people who know each other; not how a real version
would work.

**Capped at a small number of members.** Deliberate. It's a pilot.

**Self-entered data.** Nobody's calendar is being read. Members say where they're going.
That's the whole model, and it's also why it's entirely opt-in — if you don't want a
conference known, don't add it.

---

## The three asks for the post

Don't need to all land in one message, and leading with the third makes it sound like a
bigger commitment than it is.

1. **Try it** — get members using it, see if the core idea holds up
2. **Use of the CREW name** — permission for what's currently an unofficial member project
3. **Integration** — eventually build it into the CREW community platform properly

Recommended order: lead with 1, mention 2 in passing, save 3 for after people have used
it and formed an opinion.
